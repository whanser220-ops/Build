# 方案文档维护规则

本文档用于回答一个实际问题：

为什么 `docs/plans/` 里会出现“文档很多，但不是都等于当前实现”。

答案是：方案文档本来就有生命周期，关键不是让所有文档永远一样新，而是让每篇文档都明确自己属于哪一类，并在代码变化时知道该同步哪一层。

## 文档角色

`docs/plans/` 里的文档建议分成 4 类：

### 1. 当前实现基线

定义：

- 当前项目真正采用的技术主路径。
- agent 改这部分代码时，应优先参考这类文档。

要求：

- 必须强同步。
- 代码主行为变了，文档同轮就要改。

### 2. 候选方案

定义：

- 用于规划下一阶段路线、替代方案或尚未全面落地的设计。

要求：

- 不要求每次代码微调都同步。
- 但如果已经不再准备采用，应改状态或标注被替代。

### 3. 工作流说明

定义：

- 偏使用手册、工具流程、操作步骤。

要求：

- 只要入口、步骤、产物或前置条件变化，就应同步。

### 4. 历史方案

定义：

- 曾经讨论过、试过、但当前不再是主路径的方案。

要求：

- 不删除历史价值。
- 但必须显式标注“不是当前实现”。

## 推荐状态枚举

每篇方案文档头部建议至少声明这些信息：

- `状态`
  - `草案`
  - `可开工`
  - `实施中`
  - `已实现`
  - `已偏离实现`
  - `已废弃`
- `同步级别`
  - `强同步`
  - `弱同步`
  - `归档`
- `当前实现锚点`
  - 指向当前核心脚本、Shader、场景或工具入口。
- `最后实现核对`
  - 最近一次确认“文档与代码是否一致”的日期。

## 改代码时怎么同步方案

最实用的做法不是“改完代码后想起来再补文档”，而是把文档同步当成提交的一部分。

建议按这个最小流程执行：

1. 改代码前，先判断这次改动命中了哪篇“当前实现基线”。
2. 改代码时，同时记录哪些行为、入口、产物、限制发生了变化。
3. 改完后至少同步文档头部状态、相关文件、关键流程和边界说明。
4. 如果来不及完整重写正文，先把文档状态改成“已偏离实现”，并写出偏离点。

## 哪些变化一定要改文档

出现以下变化时，应同步方案文档：

- 主流程改变
- 核心入口文件改变
- 关键数据结构或产物格式改变
- 工具使用步骤改变
- 约束和边界改变
- 原方案被新方案替代

如果只是局部重构且不改变外部行为，可以只更新“相关文件”或不改正文。

## 怎么避免多个文档都像“当前方案”

推荐做法：

- 新方案接管主路径时，在新文档写“替代了谁”。
- 在旧文档头部写“已被谁替代”或“已偏离实现”。
- 在 `docs/PLANS.md` 里更新索引角色。

也就是说，真正的单一入口不是靠删除旧文档，而是靠索引和状态管理。

## 最小维护原则

不要要求每次改动都重写整篇设计稿。

真正必须保持新鲜的通常只有这些位置：

- 文档头部状态
- 当前实现锚点
- 主流程图或步骤
- 关键限制与风险
- 替代关系

只要这几处始终可信，旧正文即使还有部分历史描述，也不会太误导。
