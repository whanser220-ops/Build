# PRD：Unity 6 全量 PBD + Neighbor Grid 可乐瓶堆积碰撞系统

## 文档信息

- 版本：v0.4
- 日期：2026-04-12
- 状态：需求收敛完成，待以“胶囊体瓶子 + 立方体角色”占位模型推进技术样机
- 适用范围：Unity 6 `URP` 中大量同款可乐瓶的统一 `PBD + neighbor grid + 实例化渲染` 系统

## 背景

目标效果是一大堆相同的可乐瓶堆放在场景中，角色靠近、穿过或冲撞时，瓶子会被撞开、翻倒、滚动、互相挤压，并继续推动周围瓶子形成连锁反应。

当前新增约束：

- 目前没有正式瓶子模型
- 首版样机先使用胶囊体作为渲染占位模型
- 角色当前先使用立方体作为占位模型与交互代理
- 在正式瓶子模型到位前，当前阶段的验收重点放在碰撞传播、堆积稳定性和交互手感，而不是最终外观

本轮需求已经明确约束技术路线：

- 不做远近分层
- 不做“近处真实刚体、远处近似”的混合方案
- 不保留传统 `Rigidbody` 过渡路径
- 全部瓶子统一进入同一套 `PBD + neighbor grid` 求解流程
- 渲染统一使用实例化渲染

因此，本 PRD 不再讨论“哪条路线更稳”，而是直接定义一套可执行的全量统一架构。

## 问题定义

这个需求的核心矛盾是：

- 瓶子数量很多
- 所有瓶子都需要实时响应角色撞击
- 瓶子之间需要持续发生接触、堆积和传播
- 系统又必须保持实时运行

如果使用传统逐刚体方案，瓶子数量提升后，碰撞对数、接触稳定性和 CPU 预算都很容易失控。  
如果要坚持所有瓶子都统一参与模拟，就需要一种更适合大批量接触约束的求解方式。

本方案采用：

- `PBD` 负责统一求解位置约束、接触修正和形状保持
- `neighbor grid` 负责为全量瓶子提供近邻查询加速
- 实例化渲染负责以低提交成本输出大量同款瓶子

## 目标

- 支持单个瓶堆区域内 `500-1500` 个同款瓶子统一参与 `PBD` 模拟。
- 所有瓶子都在同一套 solver 中更新，不按距离切换物理路径。
- 角色进入瓶堆后，能够持续推动整堆内部发生局部到中尺度传播。
- 瓶子表现出可信的翻倒、滚动、堆积和挤压效果。
- 渲染层使用统一实例化路径输出全部瓶子，不切换近景/远景资源。
- 系统具备明确的 benchmark、调试统计和可持续优化入口。

## 非目标

- 不在本轮支持单瓶拾取、精确手持、玻璃破碎和瓶内液体模拟。
- 不在本轮追求严格网络同步 determinism。
- 不在本轮支持大量不同尺寸、不同拓扑瓶子的混合统一解算。
- 不在本轮引入额外的远景代理、LOD 物理路径或刚体回退路线。
- 不在本轮把角色与瓶子交互扩展为复杂玩法系统。

## 用户与干系人

- 图形程序：负责实例化渲染、缓冲组织、调试统计与性能预算。
- 物理/玩法程序：负责 `PBD` 约束、角色交互输入、边界碰撞与系统接入。
- 技术美术：负责瓶子代理结构、材质统一、视觉容差和效果验收。
- 场景/关卡：负责瓶堆摆放规模、地面边界、镜头观察点与 benchmark 场景。
- 制作负责人：负责目标平台、预算门槛和效果优先级。

## 当前假设

- 引擎版本为 Unity 6 `6000.0.46f1`。
- 渲染管线为 `URP`。
- 目标平台为 PC / 主机级 GPU。
- 系统允许使用 Compute Shader 和结构化缓冲。
- 当前暂无正式瓶子模型，首版以单一胶囊体占位网格推进样机。
- 角色交互代理当前统一使用立方体盒体，不使用胶囊体角色代理。
- 该效果是场景反馈与演出重点，因此接受较高的专项技术投入。

## 成功标准

以下门槛是当前 PRD 的原型目标，应在目标机 benchmark 后修订：

- 1080p 内部分辨率下，瓶堆系统 CPU 主线程预算建议 `<= 1.0 ms`。
- 1080p 内部分辨率下，瓶堆系统 GPU 求解与渲染总预算建议 `<= 5.0 ms`。
- 在 `1000` 个瓶子规模下，角色冲撞时系统保持稳定，无大面积爆炸式穿透。
- 在 `500 / 1000 / 1500` 三档规模下，neighbor grid 查询成本和 solver 迭代成本可被解释和统计。
- 角色撞入瓶堆后，能观察到从接触点向周围传播的连锁翻倒与滚动。
- 胶囊体瓶子占位渲染层无明显实例丢失、排序错乱或模拟/显示不同步。

## 技术路线

系统统一采用三部分组成：

- `PBD` 统一求解瓶子位置与姿态
- `neighbor grid` 为全量瓶子提供近邻候选查询
- 实例化渲染负责将求解后的瓶子姿态批量输出

这三部分必须共享同一份瓶子状态数据，不允许出现：

- 近景一套物理、远景另一套物理
- 模拟层与渲染层维护两份不同真值
- 部分瓶子走刚体、部分瓶子走 `PBD`

## 推荐架构

### 1. 统一瓶子表示

每个瓶子不直接以高精度网格参与碰撞，而是表示为一个小型刚性粒子簇：

- 每瓶推荐 `4-8` 个代理粒子
- 粒子簇保存静止形状下的相对偏移
- 每帧通过 shape matching 或等价刚性约束恢复整体瓶形
- 渲染姿态由簇中心和簇朝向提取，不直接依赖单个粒子旋转

推荐最小组成：

- `1` 个中心粒子
- `2-4` 个瓶身支撑粒子
- `1-3` 个顶部或底部稳定粒子

这样可以在控制粒子数的同时，保留瓶子翻倒、滚动和接触传播所需的基本形状信息。

### 2. 统一求解流程

每帧统一执行以下流程：

1. 写入外部输入
2. 预测粒子位置
3. 构建全量 `neighbor grid`
4. 生成近邻候选
5. 迭代求解约束
6. 回写速度与簇姿态
7. 更新实例化渲染缓冲

其中约束至少包括：

- shape matching 刚性保持
- 粒子间非穿透约束
- 地面与静态边界碰撞约束
- 角色立方体盒体或代理体碰撞约束
- 阻尼与摩擦近似项

### 3. Neighbor Grid 设计

`neighbor grid` 是全量系统的核心加速结构，负责避免暴力两两检测。

设计要求：

- 所有瓶子代理粒子每帧都写入统一网格
- 网格类型为均匀网格或哈希网格
- cell 尺寸应接近代理碰撞半径的 `1.0-1.5` 倍
- 查询范围默认覆盖当前 cell 及周围相邻 cell
- 必须输出每帧的 cell 占用、平均邻居数和最大邻居数

推荐缓冲：

- `ParticleCellIndexBuffer`
- `SortedParticleIndexBuffer`
- `CellStartEndBuffer`
- `NeighborStatsBuffer`

### 4. 角色交互

角色不直接逐瓶施加传统力，而是作为统一求解器中的外部碰撞体或冲量源：

- 角色立方体盒体进入 solver
- 对重叠粒子施加位置修正和速度扰动
- 冲刺、推挤、撞击通过不同输入 profile 调整修正强度
- 所有交互都通过同一套约束路径生效

这能保证角色碰撞与瓶子之间的传播使用相同物理语义，而不是额外开一条特殊逻辑。

### 5. 实例化渲染

渲染系统必须完全跟随统一求解器输出：

- 每个瓶子维护一个实例索引
- solver 产出的簇中心和朝向回写到实例变换缓冲
- 所有瓶子统一用实例化渲染输出，首版使用胶囊体占位网格
- 不按远近切换资源或渲染路径

渲染要求：

- 共享网格
- 共享材质
- 每实例变换矩阵或位置+旋转数据
- 可选每实例颜色扰动或标签偏移

## 核心需求

### R1：全量统一求解

- 所有瓶子都必须进入同一套 `PBD` 数据结构与更新流程。
- 不允许按距离、镜头或激活区切换物理路径。

### R2：瓶子形状保持

- 每个瓶子必须通过粒子簇和刚性约束保持总体瓶形。
- 在剧烈碰撞下允许局部近似误差，但不能退化成散沙式粒子堆。

### R3：全量 Neighbor Grid

- 每帧必须对全量瓶子代理粒子构建统一邻域网格。
- 系统必须能统计并可视化网格占用、邻居数和热点 cell。

### R4：角色碰撞一致性

- 角色与瓶子的交互必须进入统一 solver。
- 角色走路、奔跑、冲刺至少支持三档交互强度。

### R5：堆积与传播

- 系统必须支持瓶子堆积、翻倒、滚动与连锁传播。
- 当角色撞开一部分瓶子时，周围瓶子应被持续带动，而不是仅第一层响应。

### R6：统一实例化渲染

- 所有瓶子统一使用实例化渲染，不允许为局部瓶子切换单独渲染路径。
- 渲染状态与模拟状态必须一一对应。

### R7：可调试与可 benchmark

- 必须具备 solver 迭代数、substep 数、平均邻居数、最大邻居数、约束数和每帧时序统计。
- 必须具备固定 benchmark 场景，用于比较不同粒子数、网格尺寸和迭代参数。

## 里程碑

### Phase 0：最小闭环

- 固定数量瓶子初始化
- 单一地面碰撞
- 角色立方体推开瓶堆
- 全量 `neighbor grid` 构建
- 实例化渲染跟随 solver 输出

### Phase 1：稳定性版本

- shape matching 稳定
- 摩擦与阻尼参数收敛
- `500-1000` 瓶子 benchmark
- 调试面板可视化邻域网格和统计

### Phase 2：性能版本

- `1000-1500` 瓶子 benchmark
- 优化 grid 构建、排序和约束求解
- 优化角色撞击时的极端拥挤场景
- 收敛瓶子粒子数、cell 尺寸与 solver 参数

## 验收标准

- 在固定 benchmark 场景中，全部瓶子都由统一 `PBD` 系统驱动。
- 角色冲撞时，瓶子会出现连续翻倒、滚动和传播，而不是局部几个瓶子单独弹开。
- 求解过程中不存在长期大面积穿透、明显爆炸或整堆持续抖动。
- 邻域查询统计可解释，热点区域与拥挤接触分布可被定位。
- 胶囊体瓶子占位渲染层与求解层保持同步，不出现实例错位或掉帧式闪烁。

## 风险

- 全量统一 `PBD` 的工程风险和调试难度明显高于混合方案。
- 每瓶粒子数一旦过高，neighbor grid 构建和约束求解成本会快速上升。
- 每瓶粒子数一旦过低，瓶子会失去应有的形体和滚动感。
- cell 尺寸选错会导致邻居数暴涨或漏检接触。
- 在高密度堆积与角色高速冲撞同时发生时，solver 可能需要更多 substep 与迭代数。
- 如果实例化渲染与 solver 数据不同步，会产生明显视觉撕裂。
- 由于首版只用胶囊体占位，翻倒轮廓和真实可乐瓶会有视觉偏差，可能误导对最终观感的判断。

## 未决问题

- 目标平台最终预算是多少，是否必须锁定 60 FPS？
- 每个瓶子采用 `4 / 6 / 8` 个代理粒子时，哪一档最符合质量与成本平衡？
- solver 的首版参数应为多少个 substep、多少次迭代？
- neighbor grid 的 cell 尺寸应以瓶身直径、代理半径还是接触半径为基准？
- 实例化后端首版采用哪种 Unity 接口最合适，是否需要直接对接更大规模的间接实例化？
- 正式瓶子模型接入后，胶囊体占位阶段验证通过的手感和预算是否仍然成立？

## 结论

本需求现已明确收敛为一条单一路线：

- 全量瓶子统一进入 `PBD` 求解
- 全量近邻查询统一通过 `neighbor grid` 加速
- 全量渲染统一通过实例化输出

这意味着系统不会依赖远近切换、刚体回退或混合物理路径，而是要把全部工程重心放在：

- 瓶子粒子簇设计
- 邻域网格构建
- 约束求解稳定性
- 实例化渲染同步

后续工作应直接围绕这四个点做 benchmark 和技术样机验证。
